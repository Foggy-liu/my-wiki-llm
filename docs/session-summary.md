# 项目背景

本项目是对 **docs/task/tasks.md** 中 **题目一：文物 IP 内容自动化生产链设计与局部实现** 的分析与设计。

# 用户需求理解

## 用户输入示例
> "以青铜面具为主角，写一个 60 秒悬疑风短视频脚本。"

## 链路理解

用户希望完成从 **创意需求** 到 **AI视频生成Prompt** 的完整自动化链路，包含三个层次：

```
用户提问（含文物类型 + 创意要求）
    ↓
资料层：知识库检索，召回与"青铜面具"相关的史实资料
    ↓
生成层：基于召回资料生成脚本（必须严格基于资料，禁止编造）
    ↓
对接层：将脚本转化为可直接用于AI视频生成的Prompt
```

# 三个层次的核心职责

| 层次 | 核心问题 | 关键能力 |
|------|----------|----------|
| **资料层** | 知识库如何搭建？检索如何精准召回？ | Wiki式知识库、Embedding检索、史实约束 |
| **生成层** | 如何基于检索结果生成脚本？如何防止幻觉？ | RAG+生成、引用溯源、约束校验 |
| **对接层** | 如何将脚本转化为可执行的视频生成Prompt？ | Prompt模板化、多工具适配 |

## LLM Wiki 核心思路澄清

### 初始理解偏差

最初我将 Wiki 局限在"史实资料库"，但用户指出这是错误的理解。

### 正确的 LLM Wiki 理解

**Wiki = LLM 维护的"所有知识"的统一集合**，包括但不限于：
- 史实资料：`青铜面具.md`、`三星堆.md`
- 创作方法：`悬疑叙事技巧.md`、`脚本结构.md`
- 工具知识：`视频 Prompt 编写指南.md`、`镜头语言手册.md`
- 概念解释：`古蜀文明.md`、`祭祀仪式.md`

**关键洞察**：Wiki 不是"史实库"，而是"知识库"。生成层需要的格式知识、叙事技巧、框架模板都应该存在于 Wiki 中。

## 架构理解（修正版）

### 传统理解的流程（错误）
```
用户输入 → 直接去 Wiki 检索"青铜面具" → 生成
                    ↑
            没有考虑意图！
```

### 更准确的流程
```
用户输入 → 意图识别（生成层入口）
                 │
                 ├── "视频" → 调用视频格式知识 + Wiki史实
                 └── "脚本" → 调用脚本框架知识 + Wiki史实
```

### 资料层和生成层的边界

| 层级 | 职责 | 存储内容 |
|------|------|---------|
| **资料层（Wiki）** | 统一知识存储和检索 | 史实 + 格式知识 + 工具知识 + 概念 |
| **生成层** | 意图识别、格式选择、内容融合 | 根据意图调用 Wiki 中的对应知识 |

### 核心问题：用户意图高于资料

用户的观察非常重要：

> "生成创意视频" vs "生成创意视频脚本"——仅二字只差，embedding 时应该先去生成层识别用户意图。

**正确理解**：
1. **意图识别是入口**，发生在 Wiki 检索之前
2. **意图决定去哪里检索、检索什么**
3. **Wiki 不关心用户要什么格式**，只提供知识素材
4. **格式和框架由生成层根据意图决定**，Wiki 只负责内容

### 生成层的"资料"来源

生成层需要的资料分为两类：

| 类型 | 内容 | 作用 |
|------|------|------|
| **格式知识** | 脚本模板、视频 Prompt 模板、文案结构 | 决定输出是什么格式 |
| **领域知识** | 叙事技巧、镜头语言、光影设计 | 决定内容怎么组织 |

**这些知识应该统一存在 Wiki 中**，而不是分离存储。

## Embedding 的定位

### Embedding 没有被抛弃

Embedding 仍然是关键技术，只是应用位置变了：

| 场景 | 传统 RAG | LLM Wiki |
|------|---------|---------|
| **检索对象** | 原始文档碎片 | LLM 整理好的结构化词条 |
| **检索时机** | 直接匹配用户 query | 在意图识别后，针对特定知识领域检索 |

### Wiki 内部检索
- 小规模（<100 页面）：直接用 `index.md` 遍历
- 大规模（>100 页面）：Embedding 增强检索（llm-wiki.md 推荐 qmd 工具）

### 关键发现

#### 1. Wiki 的四层记忆模型

```
┌─────────────────────────────────────────────────┐
│  Procedural（程序性）  output/*                  │  可直接使用的交付物
├─────────────────────────────────────────────────┤
│  Semantic（语义性）   wiki/comparisons/ +        │  跨材料的洞察
│                       wiki/synthesis/            │
├─────────────────────────────────────────────────┤
│  Episodic（情景性）   wiki/entities/ +           │  结构化知识
│                       wiki/concepts/            │
├─────────────────────────────────────────────────┤
│  Working（工作性）    wiki/summaries/           │  单材料摘要
└─────────────────────────────────────────────────┘
```

**知识会逐层晋升**：summaries → entities/concepts → comparisons/synthesis → output

#### 2. Wiki 页面类型（5种）

| 类型 | 位置 | 说明 |
|------|------|------|
| entities | wiki/entities/ | 实体（具体事物：工具、文物、人） |
| concepts | wiki/concepts/ | 概念（设计模式、方法论、理论框架） |
| summaries | wiki/summaries/ | 材料摘要（每消化一个材料一个文件） |
| comparisons | wiki/comparisons/ | 对比分析（A vs B） |
| synthesis | wiki/synthesis/ | 综合洞察（跨材料综合） |

#### 3. 格式知识（方法论）应该存在 concepts/ 中

**之前的错误理解**：把"悬疑叙事技巧"、"脚本结构"放在生成层单独存储

**正确的理解**：这些方法论知识应该和其他知识一样，存在 Wiki 的 `concepts/` 里

#### 4. 用户意图识别的实现方式

意图识别不需要单独的系统，它通过 Wiki 的结构自然实现：
- 用户说"脚本" → Wiki 中有 `scripts/concepts/脚本结构.md`
- 用户说"悬疑" → Wiki 中有 `concepts/悬疑叙事技巧.md`
- 用户说"青铜面具" → Wiki 中有 `entities/青铜面具.md`

**意图识别变成了"在 Wiki 中找到相关概念页面"**

#### 5. Embedding 的正确定位

```
原始资料 → Ingest → Wiki 页面（结构化） → Embedding → 向量索引
                                       ↑
                             用户查询时匹配 Wiki 页面（而非原始文档碎片）
```

#### 6. Schema 和 Skills 的分离设计

- **Schema（CLAUDE.md/AGENTS.md）**：规则手册，告诉 LLM 如何维护 Wiki
- **Skills（skills/llm-wiki/SKILL.md）**：四种操作的详细流程
- **References**：按需加载的参考文档，不占用日常上下文

#### 7. index.md 使用表格格式

```markdown
| Page | Category | Confidence | Status | Updated | Description |
|------|----------|------------|--------|---------|-------------|
```

包含置信度和状态列，LLM 通过 index.md 定位页面而非遍历文件。
